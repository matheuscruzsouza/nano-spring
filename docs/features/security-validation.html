🔒 Módulo de Segurança & Validação Declarativa (v1.8.0)

A versão v1.8.0 do Nano-Spring adiciona recursos vitais para conformidade corporativa (LGPD, PCI-DSS) e proteção em tempo de execução para totens, PDVs e servidores embarcados no Android.

✨
Totalmente compatível com o padrão consagrado do Spring Boot: HTTPS transparente via Keystore, proteção contra DoS via Token Bucket e anotações @Valid com retorno automático de 400 Bad Request.

1. HTTPS / TLS Nativo via Keystore

Habilite tráfego criptografado SSL/TLS diretamente pelo application.properties sem alterar uma única linha do seu código Java:

assets/application.properties 
# Habilita o socket seguro TLS
server.ssl.enabled=true

# Caminho para o certificado (buscado em assets/ ou caminho absoluto)
server.ssl.key-store=certificates/keystore.p12

# Senha do arquivo keystore
server.ssl.key-store-password=minha-senha-segura

# Tipo do Keystore (padrão: PKCS12, suporta também BKS e JKS)
server.ssl.key-store-type=PKCS12

# Protocolos permitidos (opcional)
server.ssl.protocols=TLSv1.2,TLSv1.3

2. Proteção Anti-DoS com Rate Limiting (Token Bucket)

Dispositivos Android possuem hardware limitado. O TokenBucketRateLimiter protege o dispositivo contra sobrecarga de requisições por IP tanto globalmente quanto por rota.

A. Proteção Global

assets/application.properties 
# Habilita limitador global por IP
nano.ratelimit.enabled=true

# Requisições normais por segundo por IP
nano.ratelimit.requests-per-second=50

# Capacidade de pico (burst)
nano.ratelimit.burst-capacity=100

B. Proteção por Rota com @RateLimit

PaymentController.java 
@RestController("/api/pagamentos")
public class PaymentController {

    // Limita este endpoint a no máximo 5 requisições por minuto por cliente
    @RateLimit(requests = 5, durationSeconds = 60)
    @PostMethod("/processar")
    public ResponseEntity processarPagamento(@RequestBody PagamentoDTO dto) {
        return ResponseEntity.ok("Pagamento processado com sucesso!");
    }
}

Quando o limite é excedido, o servidor retorna instantaneamente 429 Too Many Requests com cabeçalho Retry-After:

Resposta HTTP 429 
{
  "status": 429,
  "error": "Too Many Requests",
  "message": "Rate limit exceeded for route"
}

3. Bean Validation Declarativo com @Valid

Valide DTOs recebidos no corpo das requisições declarativamente, sem escrever dezenas de if e validações manuais nos métodos:

ClienteRequest.java 
package com.minhaempresa.dto;

import com.github.matheuscruzsouza.nanospring.validation.*;
import java.util.List;

public class ClienteRequest {

    @NotNull(message = "Nome é obrigatório")
    @NotBlank(message = "Nome não pode estar em branco")
    private String nome;

    @Email(message = "Formato de e-mail inválido")
    private String email;

    @Min(value = 18, message = "Cliente deve ser maior de idade")
    @Max(value = 120, message = "Idade inválida")
    private int idade;

    @Size(min = 1, max = 5, message = "Informe entre 1 e 5 telefones")
    private List telefones;

    @Pattern(regexp = "^[0-9]{5}-[0-9]{3}$", message = "CEP deve estar no formato 99999-999")
    private String cep;
}

Validação no Controller:

ClienteController.java 
@RestController("/api/clientes")
public class ClienteController {

    @PostMethod("")
    public ResponseEntity cadastrar(@Valid @RequestBody ClienteRequest request) {
        // Só executa se passar em todas as validações!
        clienteService.salvar(request);
        return ResponseEntity.status(201).body("Cadastrado com sucesso!");
    }
}

Se qualquer campo violar as restrições, o Nano-Spring interrompe o processamento antes do método e retorna 400 Bad Request com os detalhes:

Resposta 400 Bad Request 
{

  "error": "Bad Request",
  "message": "Validation failed. 2 error(s) found.",
